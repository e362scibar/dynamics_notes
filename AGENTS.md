# AGENTS.md

Guidance for AI coding agents working in this repository.

## Overview

This repository holds personal memo material on **high-energy electron beam dynamics in accelerators**. The material is organized by topic. Each topic is kept in three forms:

| Form | Location (per topic) | Languages | Source of truth | Output |
|---|---|---|---|---|
| Jupyter notebook | `topics/<topic>/<topic>.py` | English only | Jupytext `.py` file | `.ipynb` (outputs stripped on commit) |
| LaTeX document | `topics/<topic>/main.tex` | English and Japanese | `main.tex` (bilingual source) | One PDF per language in `build/<topic>/` |
| PowerPoint slides | generated by `common/slides/build_slides.py` | English and Japanese | the topic's LaTeX document | One `.pptx` per language in `build/<topic>/` |

The English and Japanese LaTeX and slide versions must describe the same content. Equations and figures are shared between the two languages; only prose, labels, and titles differ.

## Repository layout

```text
topics/<topic>/        one directory per topic (snake_case ASCII slug, e.g. twiss_optics)
  <topic>.py           notebook source (Jupytext)
  main.tex             LaTeX document (bilingual)
  figures/             figures used only by this topic
topics/README.md       topic index and conventions
common/                shared material used by all topics
  tex/                 shared LaTeX preamble and bilingual macros
  slides/              shared slide generator (build_slides.py, README.md)
  python/              shared Python package dynamics_common (pyproject.toml, tests/)
  references/          reference index (README.md) and BibTeX database; PDFs are local only
build/<topic>/         generated outputs (git-ignored)
```

Rules:

- Put all material for a topic inside `topics/<topic>/`. Do not create notebooks, LaTeX documents, or figures for a topic outside that directory.
- Each topic has one bilingual `main.tex`. Do not create a combined PDF or deck for all topics.
- Everything shared by topics lives under `common/`. A figure used by more than one topic goes to `common/figures/`, and a helper used by more than one topic goes to `common/python/dynamics_common/`. Create `common/figures/` when the first shared figure is needed.
- Do not put topic-specific content in `common/`.

## Language rules

- **Notebooks, Python scripts, and code comments**: English only. This includes comments, docstrings, log messages, and display strings in code.
- **LaTeX and slides**: English and Japanese versions.
- **Commit messages**: English only.
- **Chat replies to the user**: Japanese, unless the user asks otherwise.

## Git rules

- **Work on the `devel` branch.** Do not commit directly to `main`. If the current branch is `main` when you start a change, switch to `devel` first (create it from `main` if it does not exist yet).
- **Do not run `git commit` unless the user explicitly asks for a commit.** Staging, editing, and building are fine without a commit request. Approval for one commit does not extend to later changes.
- Do not push, rebase, or rewrite history unless explicitly asked.
- **Never commit reference PDFs.** Under `common/references/`, only `README.md` and `references.bib` are tracked. Do not `git add -f` other files there. Check `git status` before every commit.

## Environment

- **Conda environment**: `dynamics_notes`
- **Python**: 3.14
- **Definition**: `environment.yml` at the repository root is the single place where the environment is specified. Do not hand-edit an exported lock file to add packages.

Create and activate the environment:

```bash
conda env create -f environment.yml
conda activate dynamics_notes
```

Update after changing `environment.yml`:

```bash
conda env update -f environment.yml --prune
```

Always activate the environment before running any script, notebook sync, or build.

## Commands

Replace `<topic>` with the topic directory name. Run all commands from the repository root.

### Jupytext and notebooks

Edit only the `.py` files. Sync them to the `.ipynb` files:

```bash
jupytext --sync topics/<topic>/<topic>.py
```

Execute a notebook headlessly to check that it runs (does not commit outputs):

```bash
jupytext --to notebook --execute topics/<topic>/<topic>.py
```

### LaTeX documents

Build both languages with `latexmk` and `lualatex`:

```bash
# English
latexmk -lualatex -pretex='\def\memolang{en}' -usepretex -jobname=main-en -outdir=build/<topic> topics/<topic>/main.tex

# Japanese
latexmk -lualatex -pretex='\def\memolang{ja}' -usepretex -jobname=main-ja -outdir=build/<topic> topics/<topic>/main.tex

# Clean auxiliary files
latexmk -C -outdir=build/<topic> topics/<topic>/main.tex
```

Build outputs go to `build/<topic>/`. Do not commit build outputs.

### Slides

One shared generator script builds both languages for one topic:

```bash
python common/slides/build_slides.py --topic <topic> --lang en
python common/slides/build_slides.py --topic <topic> --lang ja
```

Generated `.pptx` files go to `build/<topic>/slides-<lang>.pptx`. Do not commit them unless the user asks for a specific deck to be tracked.

### Shared Python package

```bash
pip install -e common/python    # not yet in environment.yml; add it with the first module (see common/python/README.md)
python -m pytest common/python/tests -q
```

Topic code imports the shared helpers with `from dynamics_common import ...`.

### Tests

```bash
python -m pytest -q
```

## Critical rules

### Notebooks

- **Edit `.py`, never `.ipynb`.** Jupytext-paired `.ipynb` files are generated artifacts.
- Notebooks are **English only**. Do not create Japanese notebook versions.
- Use **sympy** for every symbolic expression, derivation, or algebraic transformation. Do not hand-type a transformed equation and leave it unverified. Derive it in sympy, check it numerically when practical, and then present it using `sympy.latex()` or an equivalent that matches the LaTeX source.
- Notebook outputs are **stripped on commit by `nbstripout`**. Do not rely on committed outputs. The `.gitattributes` filter must stay configured (see below).
- Never add a topic notebook without also adding the topic's row to `topics/README.md` in the same change.
- Cite references in notebook markdown cells and comments with `[key]` (see References).

### nbstripout

`.gitattributes` routes `*.ipynb` through the `nbstripout` filter. The filter driver is registered in the local git config, which must be set once per clone:

```bash
nbstripout --install
nbstripout --status   # verify
```

Do not disable or bypass the filter (for example with `git -c filter...` tricks or by committing with `--no-verify` to skip hooks). If a notebook shows outputs in `git diff`, check that the filter is installed in this clone before committing.

### LaTeX

- The source of truth for each topic is `topics/<topic>/main.tex`, which handles both languages. Do not create separate full copies of a document for each language.
- The shared preamble and the `\memolang`, `\en`, and `\ja` macros live in `common/tex/`. Each `main.tex` loads them with `\input` using paths relative to the repository root. Do not copy the preamble into a topic.
- Language selection is done at build time with the `\memolang` macro (`en` or `ja`), passed through `latexmk -pretex`.
- Provide bilingual text with the macros `\en{...}` and `\ja{...}`. Text that is identical in both languages needs no switch.
- Equations are written once, outside any language switch, so both languages share identical math.
- Figures are shared. If a figure contains text labels, either make the labels language-neutral (symbols, axes with math only) or generate one figure per language and reference it through the same macro.
- Use `luatexja` / `luatexja-preset` for Japanese typesetting. Do not use `pdflatex` or `platex`.
- Keep package use minimal and explicit; declare every package in the preamble.
- Bibliography: use `biblatex` with `biber` and the database `common/references/references.bib`, loaded by the shared preamble in `common/tex/`. Do not use BibTeX styles for new documents. `latexmk` runs `biber` automatically once the preamble is set up.

### Slides

- **One generator, two languages, any topic.** `common/slides/build_slides.py` is the only generator; `--topic <topic>` selects the input and `--lang en|ja` selects the output. Do not write separate scripts per topic or per language.
- Reusable generator helpers (OMML conversion, JSON reading) go in `common/python/dynamics_common/`, not in the generator script.
- Do not hand-edit generated `.pptx` files.
- Slide content must be derived from the topic's LaTeX document, not written twice. The planned mechanism is that LaTeX slide-marker macros write structured entries (titles, bullet points, math strings, figure paths, speaker notes) for each language to an auxiliary JSON file during compilation, and the Python builder reads that JSON. If that mechanism is not yet implemented, say so explicitly rather than duplicating content silently.
- **Equations are native PowerPoint equations (OMML).** The pipeline is LaTeX math string → MathML (`latex2mathml`) → OMML (`mathml2omml.convert`, from the `mathml2omml-as` package) → inserted into the slide XML with `lxml`, because `python-pptx` has no equation API. Do not fall back to rendered images or mathtext unless the user asks for them.
- Each slide should carry a concise title and a small number of points. Put longer explanation in speaker notes.
- Japanese decks must set the East Asian font attribute on text runs so that the text renders in a Japanese font.

## References

Reference literature is indexed in `common/references/README.md` and stored in `common/references/references.bib`. The PDFs are local copies and are not committed.

- **Cite what you use.** When a document, notebook, or slide uses content, an equation, a figure, or a result from a reference, cite it. Use the BibTeX key from `references.bib`.
  - LaTeX: `\cite{key}`. Do not write bibliography entries inside `main.tex`.
  - Notebooks (English markdown cells and comments): `[key]`, for example `[wiedemann2015, Sec. 6.3]`.
  - Slides: put the short key in the slide footer or speaker notes. The LaTeX citations are carried into the slide JSON.
- **Paraphrase and cite.** Do not copy long passages. Reproduce a figure from a reference only after checking its license. Prefer redrawing it from the source equations with a citation.
- **Add a reference properly.** Add a BibTeX entry to `references.bib` (with a `doi` field whenever a DOI exists), add an index row to `common/references/README.md` with the source and access status, and, if the PDF is available locally, link it as `common/references/<key>.pdf` with a symbolic link (`ln -sn`) to the original file. Keep the original file and do not rename it.
- **Prefer open access.** When you suggest a reference, check whether an open-access version exists and record the access status in the index. Do not add a paywalled source without noting that it is not open access.
- Do not fabricate bibliographic data. If details are uncertain, write them with a `note` field saying so, as in `references.bib`.

## Python code style

The global Python rules in `~/.claude/CLAUDE.md` apply. In summary, for all Python files except Jupytext-paired notebooks:

- Shared Python code lives in `common/python/dynamics_common/` and has tests in `common/python/tests/`. Topic notebooks import it; they do not copy it.
- Public functions in `dynamics_common` need `pytest` tests (see `common/python/README.md`).

- Format with `black` (line length 120) and sort imports with `isort`.
- Google-style docstrings and type hints on all functions and classes.
- `pathlib.Path` for file operations; f-strings for formatting.
- No bare `except:`; no mutable default arguments; no global mutable state.
- `@dataclass` for fixed-field data; convert JSON/YAML to dataclasses early.
- `logging` with explicit levels; no debug `print` in library code.
- Name constants in `SCREAMING_SNAKE_CASE`; no magic numbers.
- Always write a decimal point in floating-point literals (`1.0`, not `1`).
- Comments and docstrings in English only.

Notebook `.py` files (Jupytext pairs) are exempt from the formatting rules above, but keep them readable, keep comments in English, and avoid hard-coded absolute paths.

## Commit messages

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <short summary>`.
- Write commit messages entirely in English.
- Common scopes: `topics`, `common`, `common/slides`, `common/python`, `common/references`, `env`, `repo`. For changes inside one topic, use the topic name as the scope (for example `feat(twiss_optics): ...`).
- Commit only when the user explicitly asks (see Git rules).

## Documentation

- Write documentation, code comments, and display strings in US English, except for the Japanese versions of LaTeX and slide content.
