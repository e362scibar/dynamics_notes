# AGENTS.md

Guidance for AI coding agents working in this repository.

## Overview

This repository holds personal memo material on **high-energy electron beam dynamics in accelerators**. The material is organized by topic. Each topic is kept in three forms:

| Form | Location (per topic) | Languages | Source of truth | Output |
|---|---|---|---|---|
| Jupyter notebook | `topics/<topic>/<topic>.py` | English only | Jupytext `.py` file | `.ipynb` (outputs stripped on commit) |
| LaTeX document | `topics/<topic>/main.tex` | English and Japanese | `main.tex` (bilingual source) | One PDF per language: `build/<topic>/<number>-<lang>.pdf` |
| PowerPoint slides | generated by `common/slides/build_slides.py` | English and Japanese | the topic's LaTeX document | One `.pptx` per language: `build/<topic>/<number>-slides-<lang>.pptx` |

The English and Japanese LaTeX and slide versions must describe the same content. Equations and figures are shared between the two languages; only prose, labels, and titles differ.

Every topic has a document number `YYYY-NNN` (for example `2026-001`) that is used to cite the topic from other documents and in the names of the output files. See [Document numbers](#document-numbers).

## Repository layout

```text
topics/<topic>/        one directory per topic (snake_case ASCII slug, e.g. twiss_optics)
  <topic>.py           notebook source (Jupytext)
  main.tex             LaTeX document (bilingual)
  figures/             figures used only by this topic
topics/README.md       topic index and conventions
common/                shared material used by all topics
  tex/                 shared LaTeX preamble and bilingual macros
  slides/              shared slide generator (build_slides.py, README.md)
  python/              shared Python package dynamics_common (pyproject.toml, tests/)
  references/          reference index (README.md) and BibTeX database; PDFs are local only
  glossary.toml        Japanese terminology glossary (single source of truth)
  glossary.md          generated index of glossary.toml
  documents.toml       document numbers of the topics (single source of truth)
  documents.bib        generated BibTeX database of the document numbers
build/<topic>/         generated outputs, named by document number (git-ignored)
```

Rules:

- Put all material for a topic inside `topics/<topic>/`. Do not create notebooks, LaTeX documents, or figures for a topic outside that directory.
- Each topic has one bilingual `main.tex`. Do not create a combined PDF or deck for all topics.
- Everything shared by topics lives under `common/`. A figure used by more than one topic goes to `common/figures/`, and a helper used by more than one topic goes to `common/python/dynamics_common/`. Create `common/figures/` when the first shared figure is needed.
- Do not put topic-specific content in `common/`.

## Language rules

- **Notebooks, Python scripts, and code comments**: English only. This includes comments, docstrings, log messages, and display strings in code.
- **LaTeX and slides**: English and Japanese versions.
- **Japanese text in LaTeX and slides**: use the plain form (だ・である調) at the end of sentences, for example 「求める。」「得られる。」「確認すること。」. Do not use the polite form (です・ます調). Keep the English versions unchanged.
- **Japanese technical terms**: follow [common/glossary.toml](common/glossary.toml), the single source of truth for term translations. Read [common/glossary.md](common/glossary.md) before translating. When a term is missing, add it to `glossary.toml` and regenerate the index with `python common/python/dynamics_common/glossary.py --write`. Do not introduce a second Japanese form for a term that already has one.
- **Commit messages**: English only.
- **Chat replies to the user**: Japanese, unless the user asks otherwise.

## Git rules

- **Work on the `devel` branch.** Do not commit directly to `main`. If the current branch is `main` when you start a change, switch to `devel` first (create it from `main` if it does not exist yet).
- **Do not run `git commit` unless the user explicitly asks for a commit.** Staging, editing, and building are fine without a commit request. Approval for one commit does not extend to later changes.
- Do not push, rebase, or rewrite history unless explicitly asked.
- **Push to both remotes.** When a push is requested, push to `origin` and to `github`. Do not push to only one of them.
  - Push `devel` first: `git push origin devel` and `git push github devel`.
  - To fast-forward `main`, run `git push origin devel:main` and `git push github devel:main`. Do not force-push `main`.
  - Whenever `main` is fast-forwarded on the remotes, fast-forward the local `main` branch as well, without being asked again. Stay on `devel` and run `git fetch . devel:main`, which refuses anything that is not a fast-forward. Do not check out `main`, and do not use `git branch -f`.
  - Check that the remotes are in sync afterwards (for example with `git fetch --all` and `git status -sb`), and that local `main`, `origin/main`, and `github/main` point to the same commit as `devel`.
- **Never commit reference PDFs.** Under `common/references/`, only `README.md` and `references.bib` are tracked. Do not `git add -f` other files there. Check `git status` before every commit.

## Commands

Replace `<topic>` with the topic directory name. Run all commands from the repository root.

### Build every topic

To build all topics at once, loop over the topic directories. The document number is looked up per topic, so the
output names stay correct when a topic is added or renumbered:

```bash
for topic in topics/*/; do
  topic=$(basename "$topic")
  [ -f "topics/$topic/main.tex" ] || continue
  NUM=$(python common/python/dynamics_common/documents.py --number "$topic")
  for lang in en ja; do
    latexmk -lualatex -pretex="\def\memolang{$lang}" -usepretex \
      -jobname="$NUM-$lang" -outdir="build/$topic" "topics/$topic/main.tex"
    python common/slides/build_slides.py --topic "$topic" --lang "$lang"
  done
done
```

The LaTeX build must run before the slide build of the same language, because it writes
`build/<topic>/<number>-<lang>.slides`. Add `-g` to `latexmk` to force a rebuild when the sources did not change but
the shared preamble did.

### Jupytext and notebooks

Edit only the `.py` files. Sync them to the `.ipynb` files:

```bash
jupytext --sync topics/<topic>/<topic>.py
```

Execute a notebook headlessly to check that it runs (does not commit outputs):

```bash
jupytext --to notebook --execute topics/<topic>/<topic>.py
```

### LaTeX documents

Build both languages with `latexmk` and `lualatex`. The job name is the document number of the topic, so the PDFs are `build/<topic>/<number>-en.pdf` and `build/<topic>/<number>-ja.pdf`:

```bash
NUM=$(python common/python/dynamics_common/documents.py --number <topic>)

# English
latexmk -lualatex -pretex='\def\memolang{en}' -usepretex -jobname=$NUM-en -outdir=build/<topic> topics/<topic>/main.tex

# Japanese
latexmk -lualatex -pretex='\def\memolang{ja}' -usepretex -jobname=$NUM-ja -outdir=build/<topic> topics/<topic>/main.tex

# Clean auxiliary files
latexmk -C -jobname=$NUM-en -outdir=build/<topic> topics/<topic>/main.tex
latexmk -C -jobname=$NUM-ja -outdir=build/<topic> topics/<topic>/main.tex
```

Build outputs go to `build/<topic>/`. Do not commit build outputs.

### Slides

One shared generator script builds both languages for one topic:

```bash
python common/slides/build_slides.py --topic <topic> --lang en
python common/slides/build_slides.py --topic <topic> --lang ja
```

Generated `.pptx` files go to `build/<topic>/<number>-slides-<lang>.pptx`, and every slide carries the document number in its footer. The LaTeX build of the same language must run first because it writes `build/<topic>/<number>-<lang>.slides`. Do not commit the decks unless the user asks for a specific deck to be tracked.

### Shared Python package

```bash
pip install -e common/python    # not yet in environment.yml; add it with the first module (see common/python/README.md)
python -m pytest common/python/tests -q
```

Topic code imports the shared helpers with `from dynamics_common import ...`.

### Tests

```bash
python -m pytest -q
```

### Glossary

`common/glossary.toml` is the single source of truth for Japanese technical terms. `common/glossary.md` is generated from it; do not edit the Markdown by hand.

```bash
# Regenerate common/glossary.md after editing glossary.toml
python common/python/dynamics_common/glossary.py --write

# Check every topics/*/main.tex for forbidden Japanese forms
python common/python/dynamics_common/glossary.py
```

`common/python/tests/test_topics_glossary.py` runs the same check under `pytest`, so a forbidden form fails the test suite.

## Document numbers

Every topic has a document number `YYYY-NNN`. It lets a document cite another document, and it makes output file names unique when files are copied into one directory.

- **Format.** `YYYY` is the year in which the number is first assigned. `NNN` is a three-digit serial number that restarts at `001` every year. A number is never changed and never reused, even when the document is withdrawn or its directory is renamed.
- **Registry.** [common/documents.toml](common/documents.toml) is the single source of truth. Each entry has the number, the topic slug, the English title, and the status (`active` or `withdrawn`). A withdrawn entry keeps its number and must not be cited by new documents.
- **BibTeX database.** `common/documents.bib` is generated from the registry. Do not edit it by hand. Regenerate it with `python common/python/dynamics_common/documents.py --write`. The shared preamble loads it next to `references.bib`.
- **Directory names.** Keep the topic directory a snake_case slug. Do not put the number in the directory name.

Add a new topic as follows:

1. Allocate the number with `python common/python/dynamics_common/documents.py --next`.
2. Add the entry to `common/documents.toml` and regenerate `common/documents.bib`.
3. Put `\setmemonumber{YYYY-NNN}` right after `\input{common/tex/preamble.tex}` in `main.tex`, and use `\date{Memo~\memonumber, YYYY}`. The shared preamble shows the number in the page header.
4. Write `Memo YYYY-NNN` in the first markdown cell of the notebook, below the title.
5. Add the row to `topics/README.md`.

Cite another document by its number: `\cite{2026-001}` in LaTeX, `[2026-001]` or `[2026-001, Sec. 9]` in notebook markdown cells and comments, and the short number in a slide footer or note. Numbers are also valid BibTeX keys, so `biblatex` lists the cited documents in the bibliography.

`python common/python/dynamics_common/documents.py` checks that every topic has an active entry, that `main.tex` and the notebook carry the registered number, that every cited number is registered and active, and that `documents.bib` is up to date. `common/python/tests/test_topics_documents.py` runs the same check under `pytest`.

## Verification after changes

After every source edit, run the build and the tests before reporting the work as done. Do not skip this for small changes.

1. Activate the `dynamics_notes` conda environment.
2. Run `python -m pytest -q` from the repository root. It also checks the glossary and the document numbers.
3. Build the affected topic's LaTeX document in both languages (see LaTeX documents). Also regenerate the slides when the LaTeX content or the slide generator changed.
4. Sync and, when a notebook changed, execute it (see Jupytext and notebooks).
5. Report failures together with their output. If a step was not run, say so.

When the shared preamble (`common/tex/`) or the slide generator changes, rebuild every topic, not only the one you edited, and check that no topic gains an overfull box or an undefined reference. Use the loop in [Build every topic](#build-every-topic) with `-g` added to `latexmk`.

Delete temporary logs you create while building. Do not leave them in the repository.

## Critical rules

### Notebooks

- **Edit `.py`, never `.ipynb`.** Jupytext-paired `.ipynb` files are generated artifacts.
- Notebooks are **English only**. Do not create Japanese notebook versions.
- Use **sympy** for every symbolic expression, derivation, or algebraic transformation. Do not hand-type a transformed equation and leave it unverified. Derive it in sympy, check it numerically when practical, and then present it using `sympy.latex()` or an equivalent that matches the LaTeX source.
- **Display equations with `display()`, not `print()`.** Use `print()` only for text and numeric messages.
- **Define every displayed equation in sympy.** Each display equation (`$$ ... $$`) in a markdown cell must also be defined in sympy in a code cell after it, and shown with `display()`. Inline math in prose is not required to have a sympy definition. Where practical, `assert` that the sympy form agrees with the earlier results in the notebook.
- Notebook outputs are **stripped on commit by `nbstripout`**. Do not rely on committed outputs. The `.gitattributes` filter must stay configured (see below).
- Never add a topic notebook without also adding the topic's row to `topics/README.md` and its document number to `common/documents.toml` in the same change. The first markdown cell below the title states `Memo YYYY-NNN`.
- Cite references in notebook markdown cells and comments with `[key]` (see References).

### nbstripout

`.gitattributes` routes `*.ipynb` through the `nbstripout` filter. The filter driver is registered in the local git config, which must be set once per clone:

```bash
nbstripout --install
nbstripout --status   # verify
```

Do not disable or bypass the filter (for example with `git -c filter...` tricks or by committing with `--no-verify` to skip hooks). If a notebook shows outputs in `git diff`, check that the filter is installed in this clone before committing.

### LaTeX

- The source of truth for each topic is `topics/<topic>/main.tex`, which handles both languages. Do not create separate full copies of a document for each language.
- Declare the document number with `\setmemonumber{YYYY-NNN}` right after the `\input` of the preamble (see Document numbers). Do not write the number anywhere else by hand; the preamble shows it in the page header.
- The shared preamble and the `\memolang`, `\en`, and `\ja` macros live in `common/tex/`. Each `main.tex` loads them with `\input` using paths relative to the repository root. Do not copy the preamble into a topic.
- Language selection is done at build time with the `\memolang` macro (`en` or `ja`), passed through `latexmk -pretex`.
- Provide bilingual text with the macros `\en{...}` and `\ja{...}`. Text that is identical in both languages needs no switch.
- Equations are written once, outside any language switch, so both languages share identical math.
- Figures are shared. If a figure contains text labels, either make the labels language-neutral (symbols, axes with math only) or generate one figure per language and reference it through the same macro.
- Use `luatexja` / `luatexja-preset` for Japanese typesetting. Do not use `pdflatex` or `platex`.
- Keep package use minimal and explicit; declare every package in the preamble.
- Bibliography: use `biblatex` with `biber` and the databases `common/references/references.bib` (literature) and `common/documents.bib` (document numbers), loaded by the shared preamble in `common/tex/`. Do not use BibTeX styles for new documents. `latexmk` runs `biber` automatically once the preamble is set up.

### Slides

- **One generator, two languages, any topic.** `common/slides/build_slides.py` is the only generator; `--topic <topic>` selects the input and `--lang en|ja` selects the output. Do not write separate scripts per topic or per language.
- Reusable generator helpers (OMML conversion, JSON reading) go in `common/python/dynamics_common/`, not in the generator script.
- Do not hand-edit generated `.pptx` files.
- **Slides are written next to the text they summarize.** Place the slide markers at the end of each numbered section of `main.tex`, after its last paragraph, under a `% Slides for this section.` comment. Only the title slide stays at the top. The slides follow the document order, because the markers are written in the order in which LaTeX processes them.
- **Every numbered section has slides.** A section may have several slides (each starts with `\slidetitle`). A section that deliberately has none carries a line `% no slide: <reason>`. `common/python/tests/test_topics_slides.py` fails when a section has neither. Unnumbered sections such as the license are not checked.
- **Update the slides together with the text.** The markers are a short hand-written summary, not generated from the equations. When you change an equation, a definition, or a convention in a section, change the markers of the same section in the same edit. Repeat each displayed equation of a slide as `\slidemath{...}`; the two copies must agree.
- **Keep slides short** so that the fixed layout of `build_slides.py` does not overflow: at most four blocks per slide (about two points and two equations), one line per point (about 75 characters in English and 38 in Japanese), and long equations split over two `\slidemath` lines (the second one starts with `\qquad`). Put longer explanation in `\slidenote`.
- The slide-marker macros in `common/tex/slides.tex` (`\slidetitle`, `\slidepoint`, `\slidemath`, `\slidefigure`, `\slidenote`) write `kind:payload` lines to `build/<topic>/<number>-<lang>.slides` during compilation. The builder reads that file with `dynamics_common.read_slide_aux`. The format is line based instead of JSON because TeX cannot escape JSON strings reliably.
- **Equations are native PowerPoint equations (OMML).** The pipeline is LaTeX math string → MathML (`latex2mathml`) → OMML (`mathml2omml.convert`, from the `mathml2omml-as` package) → inserted into the slide XML with `lxml`, because `python-pptx` has no equation API. Do not fall back to rendered images or mathtext unless the user asks for them.
- Each slide should carry a concise title and a small number of points. Put longer explanation in speaker notes.
- Japanese decks must set the East Asian font attribute on text runs so that the text renders in a Japanese font.

## References

Reference literature is indexed in `common/references/README.md` and stored in `common/references/references.bib`. The PDFs are local copies and are not committed.

- **Cite what you use.** When a document, notebook, or slide uses content, an equation, a figure, or a result from a reference, cite it. Use the BibTeX key from `references.bib`.
  - LaTeX: `\cite{key}`. Do not write bibliography entries inside `main.tex`. Another topic is cited by its document number, for example `\cite{2026-001}`.
  - Notebooks (English markdown cells and comments): `[key]`, for example `[wiedemann2015, Sec. 6.3]`. Another topic is cited by its document number, for example `[2026-001, Sec. 9]`.
  - Slides: put the short key in the slide footer or speaker notes. The LaTeX citations are carried into the slide JSON.
- **Paraphrase and cite.** Do not copy long passages. Reproduce a figure from a reference only after checking its license. Prefer redrawing it from the source equations with a citation.
- **Add a reference properly.** Add a BibTeX entry to `references.bib` (with a `doi` field whenever a DOI exists), add an index row to `common/references/README.md` with the source and access status, and, if the PDF is available locally, link it as `common/references/<key>.pdf` with a symbolic link (`ln -sn`) to the original file. Keep the original file and do not rename it.
- **Prefer open access.** When you suggest a reference, check whether an open-access version exists and record the access status in the index. Do not add a paywalled source without noting that it is not open access.
- Do not fabricate bibliographic data. If details are uncertain, write them with a `note` field saying so, as in `references.bib`.

## Python code style

The global Python rules in `~/.claude/CLAUDE.md` apply. In summary, for all Python files except Jupytext-paired notebooks:

- Shared Python code lives in `common/python/dynamics_common/` and has tests in `common/python/tests/`. Topic notebooks import it; they do not copy it.
- Public functions in `dynamics_common` need `pytest` tests (see `common/python/README.md`).

- Format with `black` (line length 120) and sort imports with `isort`.
- Google-style docstrings and type hints on all functions and classes.
- `pathlib.Path` for file operations; f-strings for formatting.
- No bare `except:`; no mutable default arguments; no global mutable state.
- `@dataclass` for fixed-field data; convert JSON/YAML to dataclasses early.
- `logging` with explicit levels; no debug `print` in library code.
- Name constants in `SCREAMING_SNAKE_CASE`; no magic numbers.
- Always write a decimal point in floating-point literals (`1.0`, not `1`).
- Comments and docstrings in English only.

Notebook `.py` files (Jupytext pairs) are exempt from the formatting rules above, but keep them readable, keep comments in English, and avoid hard-coded absolute paths.

## Commit messages

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <short summary>`.
- Write commit messages entirely in English.
- Common scopes: `topics`, `common`, `common/slides`, `common/python`, `common/references`, `env`, `repo`. For changes inside one topic, use the topic name as the scope (for example `feat(twiss_optics): ...`).
- Commit only when the user explicitly asks (see Git rules).

## Documentation

- Write documentation, code comments, and display strings in US English, except for the Japanese versions of LaTeX and slide content.
